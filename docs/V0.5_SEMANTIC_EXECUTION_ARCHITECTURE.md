# SLRM V0.5 — Semantic Execution Architecture

## Status

**Design baseline — foundation-no-guessing**

V0.4 is the functional baseline. The current regression suite contains 18 tests and is expected to remain green throughout the V0.5 refactor.

## 1. Architectural Principle

> **Data Before Logic:** knowledge and declarative semantic behavior belong in data; Python provides generic mechanisms for interpreting, validating, transforming, reasoning over, and executing that data.

A new word, concept, relation, ontology class, or supported grammar pattern should not require a new Python special case merely because the knowledge is new.

A useful test is:

> If adding knowledge requires modifying Python code, determine whether that knowledge can be represented declaratively first.

## 2. V0.5 Objective

Separate **semantic interpretation** from **semantic execution**.

Current V0.4 flow:

```text
Natural Language
      ↓
    Parser
      ↓
semantic meaning
      ↓
procedural dispatch in main.py
      ↓
Memory / Reasoning / Query
```

Target V0.5 flow:

```text
Natural Language
      ↓
 Tokenizer
      ↓
 Parser
      ↓
 Structured Meaning
      ↓
 Semantic Operation
      ↓
 Generic Semantic Executor
      ↓
 ┌──────────┬───────────┬─────────┐
 ↓          ↓           ↓
Memory   Reasoner     Query
```

## 3. Structured Meaning

The parser should produce a representation of what was linguistically expressed without directly performing the operation.

Conceptually:

```text
StructuredMeaning
├── operation
├── subject
├── predicate
├── object
├── attributes
├── rule
└── source tokens
```

The exact Python representation may evolve during implementation. The important boundary is that parsing produces a declarative semantic representation.

## 4. Semantic Operations

Operations describe mechanisms, not world knowledge.

Initial operation vocabulary:

- `ASSERT_STATE`
- `ASSERT_RELATION`
- `ASSERT_CLASSIFICATION`
- `QUERY`

These names are interface identifiers. They must not contain individual world facts such as CAT, DOG, TOM, or EATS.

The grammar/semantic data can associate a parsed meaning with an operation and, where appropriate, a relation schema.

Example conceptually:

```json
{
  "meaning": "TYPE_ASSIGNMENT",
  "operation": "ASSERT_RELATION",
  "relation": "IS_A"
}
```

The executor interprets the operation generically.

## 5. Responsibility Boundaries

### Lexicon

Owns lexical knowledge:

- words
- concepts
- parts of speech
- lexical features
- synonyms and morphology

### Grammar

Owns declarative linguistic patterns:

- token/category patterns
- semantic meanings
- mappings from linguistic structures to semantic operations

### Ontology

Owns conceptual hierarchy and inherited properties.

### Relation Schema

Owns relation behavior and constraints:

- relation type
- symmetry
- transitivity
- opposites
- subject/object constraints

### Parser

Owns linguistic parsing only.

It should not mutate memory or decide world facts.

### Semantic Executor

Owns generic execution of a structured semantic operation.

It may call Memory, Reasoner, and other mechanisms, but it should not contain individual domain knowledge.

### Memory

Owns explicit stored observations, classifications, relations, provenance, contradiction state, and identity resolution.

### Reasoner

Derives consequences from confirmed knowledge and declarative ontology/relation structures.

### Query Engine

Resolves structured questions against memory and reasoning mechanisms.

### Response Generator

Turns validated results into natural-language output. Response templates should progressively become declarative rather than accumulating procedural assumptions.

### Main

Should eventually become orchestration only:

```text
input → parse → execute/query → respond
```

It should not become the location where new linguistic meanings are implemented.

## 6. No Guessing Constraint

The V0.5 refactor must preserve the following behavior:

- Unknown entities remain `UNKNOWN`.
- An observation does not classify an entity.
- A candidate interpretation is not an asserted fact.
- Derived facts are not stored as asserted facts.
- Explicit user classification can update an entity.
- Identity can resolve observations to a canonical entity only through explicit identity data.

No semantic executor operation may silently convert uncertainty into a fact.

## 7. Knowledge vs Mechanism Test

### Knowledge — data

```text
CAT is a FELINE
FELINE is a MAMMAL
MAMMAL is an ANIMAL
CAT has no directly stored duplicate inherited properties
```

### Mechanism — Python

```text
walk parent relationships
validate relation constraints
canonicalize identity components
detect contradictions
execute a declared operation
```

The mechanism may be generic even when the data it processes is specific.

## 8. Migration Strategy

V0.5 should be implemented incrementally.

### Step 1 — Define structured semantic operations

Introduce the representation and operation vocabulary without removing the existing execution path.

### Step 2 — Extend declarative grammar/semantic data

Add operation metadata to the existing rules where required.

### Step 3 — Implement Semantic Executor

Create generic operation handlers. Handlers operate on structured data and schemas rather than individual words or concepts.

### Step 4 — Route existing statements through the executor

Replace procedural semantic branches in `main.py` one class of operation at a time.

### Step 5 — Preserve V0.4 behavior

Run the existing 18-test suite after every meaningful migration step.

### Step 6 — Refactor response generation

Move reusable response structure toward declarative templates after semantic execution is stable.

### Step 7 — Add architectural regression tests

Tests should explicitly prevent reintroduction of embedded world knowledge into procedural code.

## 9. Non-Goals for V0.5

V0.5 is not primarily about:

- adding a large dictionary
- adding many English grammar rules
- adding more ontology concepts
- building an LLM
- probabilistic guessing
- replacing explicit reasoning with statistical inference

The objective is to establish a scalable semantic execution foundation first.

## 10. Definition of Done

V0.5 is architecturally complete when:

1. Existing V0.4 tests remain green.
2. Parser output is cleanly separated from execution.
3. Semantic operations can be declared in data.
4. Generic execution does not require word-specific branches.
5. Adding a new domain concept does not require changing the executor.
6. Unknown remains distinct from false and from guessed classifications.
7. Memory continues to store explicit facts with provenance.
8. Derived knowledge remains derivable rather than being silently asserted.
9. `main.py` is reduced toward orchestration rather than semantic business logic.
10. Response generation has a defined path toward declarative templates.

## 11. Architectural Rule

The strongest rule for future SLRM development is:

> **Do not teach the engine by adding special cases. Teach the system by adding structured knowledge and relationships.**

Python should become more general as SLRM becomes more knowledgeable.
